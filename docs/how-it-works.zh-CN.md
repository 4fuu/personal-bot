# 工作原理：轮次、上下文与记忆

`personal-bot` 为每个账号维护一个长期运行的模型会话，同一时间只处理一轮。跨轮次保留的信息存放在三个地方：按 token 预算轮换的上下文窗口、模型自己撰写的笔记，以及只追加不修改的自身事件日志（记录每一轮输入、工具调用、发送结果与窗口轮换）。本文说明一轮如何开启、消息如何合并与排队、上下文窗口如何在不破坏提示词缓存的前提下轮换、笔记如何管理，以及这套机制与其他同类项目的对比。

## 什么会开启一轮

每一轮都有明确的触发原因，并会记录在管理面板的日志中：

- **收到消息：** 私聊消息，或群聊中 @模型、引用回复模型、提及模型昵称 / 别名 / 关键词的消息，会按该会话的策略开启一轮。未点名的普通群聊消息，在模型决定主动接话时也会开启一轮（见下文）。
- **唤醒词：** 模型在不发言或进入等待并结束当前轮时，可以在该会话里留下几个唤醒词。此后六小时内，只要群友或私聊对象提到其中任意一个词，即使没有点名也会触发新一轮。该会话一旦开启下一轮，此前留下的唤醒词即自动清空。
- **延时等待：** 模型可以在结束本轮时设定等待时长（1 分钟至 24 小时），到点后重新打开该会话查看最新消息。同一会话最多连续等待 10 次；若到点前该会话因其他原因先开启了新一轮，原定的等待自动取消。
- **定时任务：** 支持一次性或按周期重复的定时任务，到点后在目标会话开启一轮，并将任务备注作为该轮输入。定时任务只能在管理员的私聊中创建、修改或取消，且调用时必须引用该管理员发出的消息。若停机或暂停期间错过了触发时间，延迟在 1 小时以内的任务会在恢复后补跑一次，超过 1 小时的则直接跳过并记入日志。
- **空闲轮：** 当距离上一轮开始已超过设定的分钟数、且期间没有任何新轮次时，系统会为模型开启一轮不属于任何聊天会话的自由时间。模型可以利用这一轮自主搜索网页、阅读资料、调用 MCP 工具、整理笔记，也可以直接静默结束。默认关闭（`0` 分钟），可在面板 **高级** 页调整间隔。

任何类型的轮次启动都会重置空闲轮计时器。等待、唤醒词和定时任务均持久化保存在 SQLite 中，容器重启后自动恢复，且不会在停机恢复后积压连发。

## 消息合并、群聊插话与排队

- **按会话合并消息：** 会话中连续发来的多条消息会先聚合成一批，再统一决定是否开轮：群内安静时等待 2 秒，上一轮仍在执行时等待 5 秒，同一人连续打字时等待 2 秒，换人接话时等待 0.5 秒，有人 @模型时最多等待 1 秒，整批最长等待 8 秒（全部按消息到达驱动服务的时间计算，避免网络延迟把同一批消息拆散）。
- **群聊主动插话：** 在允许主动接话的群里，只 @了其他成员而未 @模型的消息批次会被直接忽略。其余批次先由 [Jev](https://typesafe.ai/) 评估此刻接话是否自然，随后系统会根据模型刚在该群发言的间隔、近期发言占比、该群设定的“话痨度”以及时段安静规则扣除一定分数（默认最大扣分上限为 `0.3`）。如果批次中有人 @模型，扣分会减免 `0.1`。最终得分达到阈值才会开启一轮。
- **沉默退避：** 如果模型在某个群里连续两批消息都没有发言（无论是插话评估未通过，还是模型开轮后选择保持沉默），该群下一次插话评估会推迟 15 秒；此后每多一次不发言，推迟时间翻倍，最高 5 分钟。推迟期间新消息会继续攒在同一批次里而不会丢失；一旦有人 @模型、提及昵称 / 别名 / 关键词、命中唤醒词，或待处理消息累计达到 6 条及以上，推迟会立即解除。
- **回复时机：** 批次通过触发判断后，可由 [Jev](https://typesafe.ai/) 进一步评估应该立即回复、稍作停顿还是多等片刻看看有没有后文（被点名或管理员发话时最多等 30 秒，其余按私聊 / 群聊各自的上限控制，并附加 ±20% 随机抖动）。等待期间若又有新消息到达，会并入同一批次一起交给模型。
- **轮次排队：** 整个账号同一时间只运行一轮。私聊与被点名的消息优先级高于群聊插话和定时唤醒；同时设有“饿等上限”（默认 120 秒），等待超时的会话会直接排到队首。在同一优先级内，[Jev](https://typesafe.ai/) 可以按紧急程度调整排队顺序。

## 一轮之内会发生什么

- **轮中插入新消息：** 当前轮次正在执行时，如果所在会话又来了新消息，系统会在两次工具调用之间把新消息直接交入当前轮次，让模型在回复前看到对话的最新进展。若当前运行的是空闲轮，任何会话中通过了合并与触发判断的消息批次都会直接交入该空闲轮。恰好在轮次结束瞬间到达的消息则会退回队列，留作下一轮处理。
- **可选发言与外发审核：** 模型只有显式调用发送工具，文字或表情才会发往聊天窗口；一句话不说直接结束轮次是完全正常的。每次发送都必须标明所依据的引用（消息、笔记或自身历史记录）。气泡发出前，宿主会先拦截跨会话引用的私聊或机密信息（除非引用了管理员的授权消息），过滤所有已存保密变量值，再交由 [Jev](https://typesafe.ai/) 逐条气泡审核。
- **自主记录兴趣：** 模型在聊天或浏览时遇到感兴趣的话题与信息会主动记入笔记，供后续轮次、延时回看或空闲轮继续跟进。

## 单一会话与滚动上下文窗口

每个账号自始至终保持同一个身份与历史，但它的工作记忆并不是一条无限增长的对话记录，也不会在原会话中反复把旧对话压缩成摘要，而是由一串按 token 预算轮换的上下文窗口组成：

- **固定前缀以保持缓存命中：** 在一个窗口的生命周期内，系统提示词（System Prompt）和窗口初始数据（Bootstrap）完全固定不变——笔记按 ID 固定排序，前缀中不放动态时间戳或计数器，从而保证模型服务商的 Prompt Cache 在该窗口的每一轮中持续命中。
- **分阶段尾部提醒：** 随着窗口 token 用量上升，系统会在最新一轮输入的末尾追加提醒（绝不改动已缓存的前缀）：
  - 用量达到窗口上限的 **15%、30%、50%** 时：提醒模型新建或更新笔记；
  - 用量达到 **60%、70%、80%** 时：提醒模型在话题告一段落时更新笔记、写好交接备忘并主动轮换窗口；
  - 接近**硬上限**（`窗口大小 - min(16k, 窗口大小 / 4)`）前：发出最后一次提醒，告知下一轮到达硬上限时将由系统直接强制轮换。
  每条提醒都附带当前窗口的真实 token 用量，并明确标注这是系统提醒而非用户请求。如果单轮用量一次跨越多个档位，只发送已跨过的最高一档提醒。

## 笔记：长期记忆

笔记由模型自行撰写与维护，是跨窗口保留知识的长期记忆。

- **单行摘要：** 每条笔记都必须附带一句不超过 200 字的摘要。搜索结果和每个新窗口开头的活跃笔记列表只展示摘要而不展开正文，因此即使携带 20 条活跃笔记也只占用很少的 token；模型需要细节时再按需读取对应笔记的正文。修改笔记正文时必须同步更新摘要。
- **数量额度与 token 预算：** 每个窗口默认最多新建 10 条笔记（修改已有笔记不占新建额度）。同时，活跃笔记共享窗口的 token 预算：总占用达到窗口的 15% 时开始提醒精简，超过 20% 时拒绝继续扩写，但缩短或删除旧笔记始终允许。
- **轮换时自动筛选活跃笔记：** 模型不能手动置顶笔记。每次窗口轮换时，系统按固定规则为下一窗口挑出活跃集合（默认最多 20 条，且总长度不超过窗口的 15%）：
  1. 管理员在面板中设为 **常驻** 的笔记；
  2. 在刚结束的窗口中新建或修改过的笔记；
  3. 其余笔记按带窗口衰减的使用度得分排序（发送时直接引用权重最高，所引用的消息或历史记录与某条笔记当前版本的证据 / 消息区间重合时获得一层间接加分，读取和搜索命中权重较低），并由 [Jev](https://typesafe.ai/) 对排在前面的候选笔记做最多 15% 的加权微调。
- **只追加修订与来源锚点：** 笔记从不覆盖旧内容。每次新建、修改或删除都会追加一个新版本，并由宿主自动记录当时的锚点（所属窗口、事件记录、所在会话、消息位置、引用的证据以及所概括的消息区间），因此任何版本都能随时还原当时的完整上下文。

## 窗口轮换与新窗口的初始内容

上下文窗口可通过三种方式轮换：

- **模型主动轮换：** 当窗口 token 用量达到 60% 及以上时，模型可填写四项简短交接备忘（当前话题、进展、待办、约定，上限约 4,000 token）并开启新窗口；用量不足 60% 时调用会被拒绝，避免过早丢弃上下文。
- **达到硬上限自动轮换：** 当用量触及硬上限时，系统自动关闭当前窗口并开启新窗口，此时不附带交接备忘。
- **管理员手动轮换：** 在面板 **概览** 或 **人设** 页点击 **立即轮换**，填写轮换理由后即可在下一轮边界切换到新窗口（不受 60% 用量限制），所填理由会直接放在新窗口开头的首行。

除账号的第一个窗口外，每个新窗口开头都包含一段固定的衔接说明（手动轮换时上方还会附上管理员填写的理由），随后依次是交接备忘（若有）、活跃笔记摘要列表、本次轮换归档的笔记标题，以及当前会话的近期消息。若新窗口没有交接备忘，衔接说明会引导模型按固定顺序恢复上下文——先读活跃笔记，再看最后一条锚点附近的消息，接着按锚点查自身历史记录，最后使用全文搜索——确保查得到的事情绝不让聊天对象重复第二遍。

## Jev：结构化判断与安全把关

[Jev](https://typesafe.ai/) 是 TypeSafe AI 的决策模型。它从不撰写聊天回复，也不调用任何工具；宿主向它发起结构化的是非题（返回 0–1 概率）和分档打分题（返回 0–2 分数），再结合代码中的硬性边界做出决定：

- **群聊插话（0–1 概率）：** 判断当前群聊是否适合自然接话，再减去宿主的发言频率扣分。在允许主动接话的群中默认生效。
- **回复时机（0–2 打分）：** 判断应当立即回复、稍作停顿还是多等一会儿后续消息。默认处于 **只记录不生效** 模式。
- **排队顺序（每个等待会话 0–2 打分）：** 在同一优先级内评估各等待会话的紧急程度。默认处于 **只记录不生效** 模式。
- **引用回复（0–1 概率）：** 判断回复的首个气泡是否需要引用对方的消息（目标消息距今超过 30 条或 10 分钟时强制引用）。默认处于 **只记录不生效** 模式。
- **外发审查（每条气泡 0–1 概率）：** 每次发送前逐条气泡检查：
  - **泄露密钥**：是否包含完整的 API key、令牌、密码、数据库密钥或验证码。始终启用；一旦 Jev 不可达，外发审查立即按失败关闭处理，不发出任何消息。
  - **没标引用**：是否提到了具体的人或事却未在引用或近期对话中有据可查。默认 **关闭**。
  - **自我重复**：是否在重复当前会话里自己刚刚说过的话。默认处于 **只记录不生效** 模式。
- **沙箱出网域名判定（0–1 概率）：** 当沙箱内的命令请求访问既不在放行名单、也不在拦截名单中的新域名时，由 Jev 判断该命令是否合理需要访问该域名、且不属于公开粘贴或数据外传服务。通过则记入放行名单，拒绝则记入拦截名单，Jev 不可达时默认拒绝。
- **轮换时活跃笔记打分（每条候选笔记 0–2 打分）：** 窗口轮换时对最多 8 条候选笔记评估下一窗口用到的可能性，在规则使用分基础上做最多 15% 的微调。

对于会话、排队和外发审查中的可配置判断项，管理面板支持单独调整阈值、用自然语言补充额外判断标准，并在 **关闭**、**只记录不生效**（照常询问 Jev 并记入日志，但实际仍按默认规则执行）和 **启用** 三种模式间切换。

凡是涉及会话上下文的判断，宿主都会从 Jev 的 32,000 token 窗口中划出最多约 6,000 token 的近期消息片段——优先从最早的完整消息开始裁剪，绝不把单条消息截成两半，并在状态中标明省略了多少条旧消息。所有请求在发往 Jev 前都会先脱敏抹去已存的保密变量值；只判断局部上下文的检查项（引用回复、自我重复、外发审查、活跃笔记打分）不会传入人设信息。

## 与其他项目的对比

下表根据各项目截至 2026-10-26 的公开文档整理，对比 `personal-bot` 与四个相关项目在上下文窗口与长期记忆上的设计取舍：

| 项目 | 定位 | 上下文窗口管理 | 长期记忆机制 |
| --- | --- | --- | --- |
| **personal-bot** | 自托管的单账号个人助理 | 固定前缀的滚动窗口、分阶段 token 提醒、轮换时撰写四项交接备忘；历史窗口原样保留并可检索 | 模型自行撰写的笔记：带单行摘要、token 预算、带消息锚点的只追加修订，以及每次轮换由宿主筛选的活跃笔记集合 |
| [AstrBot](https://github.com/AstrBotDevs/AstrBot) | 面向多 IM 平台的聊天机器人框架 | 按会话管理上下文，达到模型窗口 82% 时自动压缩：默认按整轮丢弃最早对话，或调用模型总结摘要并保留最新 15% | 核心不内置对话长期记忆；提供用于文档检索的知识库，并支持按需注入群聊历史 |
| [MaiBot](https://github.com/Mai-with-u/MaiBot) | 面向群聊场景的聊天机器人框架 | 维护近期消息滑动窗口，裁切旧消息时由专用模型生成摘要 | A-Memorix：对抽取出的记忆做向量、图谱与 BM25 混合检索，默认按聊天流相互隔离 |
| [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) | DeepSeek 开源的智能体运行框架 | 从只追加的会话日志派生上下文；达到路由模型窗口 80% 时自动先裁剪超长工具输出，再压缩旧对话并原样保留最新 16% | 框架本身不内置记忆存储；参考配置通过 MCP 接入外部记忆服务端 |
| [pi](https://github.com/earendil-works/pi) | 本项目所基于的 TypeScript 智能体框架 | 会话保存为只追加的树结构；接近窗口上限时自动将旧轮次压缩为摘要，并原样保留最新约 20,000 token（也支持手动 `/compact`） | 将项目说明文件与技能作为上下文加载；不包含面向聊天的长期记忆 |

`pi` 与 DeepSeek Harness 都在单一会话内就地把早期对话替换成摘要；`personal-bot` 则选择结束旧窗口、带着交接备忘和活跃笔记摘要开启新窗口，同时把旧窗口的原始记录完整保留下来供工具检索——轮换时只付一次缓存未命中的代价，历史记录永远不会因反复总结而失真。AstrBot 与 MaiBot 在单会话压缩之上叠加外部检索库（AstrBot 知识库、MaiBot 的 A-Memorix），而 `personal-bot` 让模型像人记笔记一样自己提炼、更新并在发言时显式引用笔记，所有知识都带有可追溯的原始消息锚点。
